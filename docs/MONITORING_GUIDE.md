# 모니터링 가이드 — 또바바 백엔드

## 구성 요약

| 도구 | 역할 | 접속 |
|------|------|------|
| **Sentry** | 에러 발생 시 즉시 알림 | sentry.io |
| **PostHog** | 유저 행동 분석 대시보드 | posthog.com |

---

## 왜 이 조합인가

모니터링은 크게 두 가지 질문으로 나뉜다.

- **"서버가 괜찮아?"** → Sentry
- **"유저가 앱을 잘 쓰고 있어?"** → PostHog

이 두 질문을 하나의 툴로 다 커버하는 건 현실적으로 어렵다. 아래에서 각각 왜 이 툴을 골랐는지 설명한다.

---

### Sentry를 고른 이유

**검토한 대안들**

| 툴 | 특징 | 탈락 이유 |
|----|------|----------|
| **Datadog** | 서버 메트릭 + 에러 + 유저 행동 올인원 | 월 수십만원, 지금 규모에 과함 |
| **New Relic** | Datadog과 비슷한 올인원 | 무료 티어 100GB 초과 시 월말까지 접근 차단되는 정책이 불안정 |
| **Grafana + Prometheus** | 서버 메트릭 시각화 | 에러 알림 기능 없음, 설정 복잡 |
| **Sentry** | 에러 트래킹 특화 | ✅ 선택 |

**Sentry를 선택한 이유**
- 에러 트래킹 분야에서 업계 표준
- FastAPI, SQLAlchemy, Redis 자동 연동 지원
- 에러 알림 외에도 API 응답시간, 느린 DB 쿼리까지 추적 가능 (APM 기능 포함)
- 무료 티어로 초기 단계 충분히 커버 (5,000 에러/월)
- 설치 30분, 코드 수정 최소화

---

### PostHog를 고른 이유

**검토한 대안들**

| 툴 | 특징 | 탈락 이유 |
|----|------|----------|
| **Mixpanel** | 유저 행동 분석 강자 | 무료 티어 제한적, 국내 레퍼런스 적음 |
| **Amplitude** | 대기업들이 많이 씀 | 무료 티어 제한, 세팅 복잡 |
| **DB 직접 로그** | PostgreSQL에 이벤트 테이블 | 분석하려면 SQL 직접 짜야 함, Funnel/Retention 차트 없음 |
| **PostHog** | 오픈소스 기반 유저 행동 분석 | ✅ 선택 |

**PostHog를 선택한 이유**
- 유저 행동(Funnel, Retention) + **LLM 분석(Gemini 비용/속도)** 을 하나의 대시보드에서 볼 수 있음
- Gemini 공식 지원 — 또바바는 Gemini를 LLM으로 쓰고 있어서 바로 연동 가능
- 무료 100만 이벤트/월 — 초기 단계에서 비용 없음
- 오픈소스라 나중에 트래픽 많아지면 self-hosted로 전환 가능 (비용 절감)
- 설치 시 마법사가 이벤트 코드까지 자동 생성해줌

## Sentry — 에러 트래킹

### 왜 쓰냐
배포하고 나면 에러가 나도 유저한테 연락 오기 전까지 모른다. Sentry는 에러가 터지는 순간 자동으로 알림을 보내고, 어떤 코드 줄에서 왜 터졌는지까지 기록해준다. 터미널 로그를 직접 볼 수 없는 배포 환경에서 필수다.

### 이런 상황에 씁니다
- 배포 후 API가 500 에러를 뱉을 때
- 어떤 유저가, 어떤 요청에서, 왜 에러가 났는지 파악할 때
- 같은 에러가 몇 번이나 반복됐는지 확인할 때

### 대시보드에서 볼 수 있는 것
- **Issues** — 발생한 에러 목록. 에러 종류별로 그룹핑됨
- **스택트레이스** — 에러가 코드 어느 줄에서 났는지
- **발생 빈도** — 이 에러가 오늘 몇 번 터졌는지
- **Performance** — API 엔드포인트별 응답시간, 느린 요청

### 접속 방법
1. [sentry.io](https://sentry.io) 접속
2. 팀장에게 초대 링크 받아서 프로젝트 참여
3. **Issues** 탭에서 에러 목록 확인

### 알림 설정
에러 발생 시 이메일로 자동 알림이 와요.
Slack 연동도 가능 (Settings → Integrations → Slack)

## PostHog — 유저 행동 분석

### 왜 쓰냐
서버가 잘 돌아가는 것과, 유저가 앱을 잘 쓰는 것은 다른 문제다. "채팅 시작한 사람 중에 실제로 구매/포기 결정까지 간 사람이 몇 %야?", "어느 단계에서 많이 나가?" 같은 질문은 Sentry로 알 수 없다. PostHog는 유저가 앱 안에서 어떤 행동을 하는지 이벤트로 기록하고, 이걸 차트와 퍼널로 시각화해준다. 또바바가 실제로 유저한테 잘 작동하는지 데이터로 확인하는 용도다.

### 이런 상황에 씁니다
- 유저가 채팅 어느 단계에서 이탈하는지 볼 때
- 구매 vs 포기 비율 확인할 때
- 신규 가입자 추이 볼 때
- Gemini LLM 응답 속도/비용 확인할 때

### 현재 수집 중인 이벤트

| 이벤트 | 발생 시점 |
|--------|----------|
| `user_signed_up` | 회원가입 완료 |
| `user_logged_in` | 로그인 |
| `persona_updated` | SBTI 페르소나 저장 |
| `favorite_shops_updated` | 관심 쇼핑몰 설정 |
| `chat_started` | 상품 URL 입력 후 채팅 시작 |
| `survey_submitted` | 설문 완료 |
| `chat_exited` | 채팅 종료 (구매/포기 결정) |

### 대시보드에서 볼 수 있는 것

#### Funnels (퍼널)
채팅 시작 → 설문 완료 → 채팅 종료까지 단계별로 몇 명이 이탈하는지

```
chat_started   100명
  ↓
survey_submitted  70명  (30명 이탈)
  ↓
chat_exited     50명  (20명 이탈)
```

#### Insights
- 일별/주별 신규 가입자 수
- 가장 많이 쓰는 기능
- 유저별 행동 타임라인

#### Persons
특정 유저가 앱에서 뭘 했는지 전체 흐름 조회 가능

### 접속 방법
1. [posthog.com](https://posthog.com) 접속
2. 팀장에게 프로젝트 초대 받기
3. 왼쪽 메뉴에서 **Insights** 또는 **Persons** 탭 확인

## 로컬 개발 시 주의사항

로컬에서 테스트하면 PostHog/Sentry에 데이터가 올라가요.
`.env`에서 아래처럼 설정하면 로컬 이벤트를 분리할 수 있어요:

```env
APP_ENV=local
```

Sentry 대시보드에서 `environment: local` 필터로 구분 가능.

---

## 환경변수 (팀원 `.env` 설정)

팀장에게 아래 값들 받아서 `.env`에 추가:

```env
SENTRY_DSN=https://...@sentry.io/...
POSTHOG_PROJECT_TOKEN=phc_...
POSTHOG_HOST=https://us.i.posthog.com
```
