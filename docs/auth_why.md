# 로그인 방식 선택 이유

## OAuth 2.0이란?

소셜 로그인(구글, 카카오 등)을 구현할 때 쓰는 표준 프로토콜이에요.
"구글한테 허락을 받아서 유저 정보를 가져온다"는 흐름이에요.

OAuth 2.0 안에서도 구현 방식이 여러 개 있어요.

---

## 방식 1: Authorization Code Flow

```
1. 프론트 → 구글 로그인 페이지로 리다이렉트
2. 유저가 구글에서 로그인
3. 구글 → 백엔드 콜백 URL로 code 전달
4. 백엔드 → 구글에 code로 액세스 토큰 교환
5. 백엔드 → 구글 API로 유저 정보 조회
6. 백엔드 → 우리 JWT 발급
```

**장점**
- 백엔드가 흐름 전체를 통제
- 보안적으로 검증된 방식

**단점**
- 콜백 URL 관리 필요
- 백엔드가 구글 API를 직접 호출해야 함
- 모바일 앱에서 리다이렉트 처리가 복잡함
- 구현이 복잡함

---

## 방식 2: ID Token 검증 (우리가 선택한 방식)

```
1. 프론트에서 구글/카카오 SDK로 직접 로그인
2. SDK가 ID Token 발급
3. 프론트 → 백엔드로 ID Token 전달
4. 백엔드 → 구글/카카오 공개키로 토큰 서명 검증
5. 백엔드 → 토큰에서 유저 정보 추출
6. 백엔드 → 우리 JWT 발급
```

**장점**
- 구현이 단순함
- 콜백 URL 불필요
- 모바일 앱에 적합 (Flutter, React Native 등)
- 백엔드가 구글 API를 추가로 호출할 필요 없음
- ID Token은 구글/카카오가 서명한 JWT라 위변조 불가

**단점**
- 프론트에 SDK 설정 필요

---

## 왜 방식 2를 선택했나?

**우리 서비스는 Flutter 앱이에요.**

Flutter에는 `google_sign_in`, `kakao_flutter_sdk` 같은 공식 SDK가 있어요.
이 SDK들이 로그인 UI, 인증 흐름을 다 처리해주고 ID Token만 뱉어줘요.

방식 1은 웹 서비스에서 백엔드가 브라우저 세션을 직접 관리할 때 쓰는 방식이에요.
Flutter 앱에서 방식 1을 쓰면 리다이렉트 처리, 딥링크 설정 등 불필요한 복잡함이 생겨요.

결론: **Flutter 앱 + 소셜 로그인 = ID Token 방식이 표준**

---

## 일반 로그인은?

일반 로그인은 OAuth와 무관해요.
직접 이메일 + 비밀번호를 받아서 bcrypt로 검증하고 JWT를 발급하는 방식이에요.

FastAPI 예제에서 `OAuth2PasswordBearer`가 나오는 건, Swagger UI에서 자물쇠 버튼으로 인증하는 기능을 붙이기 위한 거예요. 실제 인증 로직과는 별개예요. 우리는 JSON으로 받고 있어서 그 방식을 쓰지 않아요.

## 전체 요약

| | Authorization Code Flow | ID Token 방식 (우리) |
|--|--|--|
| 적합한 환경 | 웹 | 모바일 앱 |
| 구현 복잡도 | 높음 | 낮음 |
| 콜백 URL | 필요 | 불필요 |
| 보안 | 높음 | 높음 (구글/카카오 서명 검증) |
| 백엔드 API 추가 호출 | 필요 | 불필요 |
